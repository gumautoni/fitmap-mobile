# ADR 0007 — Store Private Media in Object Storage

## Status

Accepted

## Context

FitMap includes private user media, especially progress photos.

Storing image binaries directly in the relational database would increase database size, backup cost and operational complexity.

Keeping only local mobile file URIs is also insufficient because those references are not durable across devices, reinstalls or long-term use.

The application therefore needs persistent media storage while preserving user privacy and backend authorization.

## Decision

Private media files will be stored in **object storage**.

PostgreSQL will store the associated metadata and storage reference rather than the binary file itself.

Media access must remain private.

The backend is responsible for authorizing media operations and may provide short-lived upload or download access to object storage when appropriate.

The mobile application must never receive permanent object-storage credentials.

Storage object keys should be generated by the application rather than directly derived from user-provided filenames.

Relevant metadata may include information such as:

- owner;
- storage key;
- media type;
- creation time;
- optional relationship to a workout session.

The amount of stored metadata should remain limited to what the product actually needs.

The database and object storage do not share a distributed transaction. Media workflows must therefore account for partially completed operations and support cleanup or reconciliation when needed.

Uploaded files must be validated before being treated as trusted application media.

The specific object-storage provider is intentionally deferred.

## Consequences

### Positive

- relational data remains separate from large binary objects;
- media can be stored durably across devices;
- access remains controlled by backend authorization;
- the storage provider can be selected or changed without redefining the domain model;
- temporary access reduces exposure of private files.

### Trade-offs

- database and object storage consistency must be handled explicitly;
- upload and deletion flows require cleanup behavior;
- media access introduces additional infrastructure compared with local-only storage.

These costs are appropriate for persistent private media.

## Alternatives considered

### Store images directly in PostgreSQL

Not selected because large binary media does not need to share the same storage and backup characteristics as FitMap's transactional data.

### Store only local file URIs

Rejected because local URIs are device-specific and are not reliable persistent references.

### Public object URLs

Not selected because progress photos are private user data and should not be publicly accessible by default.
